# Independent Provenance client

The Provenance family is separate from the existing transaction circuits and Note/Credit spending APIs. It has depth 32, exactly 13 public inputs, and capacities 1–10, then 20–190 in steps of 10. The trusted release manifest SHA-256 is `f90f2ce43218de158c6392fa19e6517dda703c35823a4aa5bfc20b50788ad282`.

Sync authenticated public artifacts from a local protocol checkout:

```sh
python3 scripts/sync-provenance.py ../invisi-protocol
```

This checks the pinned manifest and every artifact/VK digest before copying 28 independent artifacts and keys into `.cache/provenance/`. Existing main circuit manifests, assets and version numbers remain separate. The cache is generated and ignored by Git. The reviewed manifest is tracked with this SDK; updating its pin requires an explicit release review.

Configure scope (chain, protocol, policy), current chain generation, provider, trusted Ed25519 public keys indexed by signingKeyId, and the reviewed manifest digest locally. Responses never establish trust. Certificate payloads use the fixed 301-byte encoding and raw 64-byte Ed25519 signatures. Empty-tree certificates are supported, but proof sources must contain at least one leaf.

The v1 metadata methods `provenance_getVersion` and `provenance_getStatus` are policy-scoped. SDK clients always send `params: [{policyId: "0x<32-byte pinned policy>"}]` from their local trust context, including for a non-default policy. They still reject a response for another policy; the service default is never used as a substitute.

The recommended flow is: fetch a signed root, verify its trust and generation, locally replay paginated public leaves at that fixed root, check contiguous indexes and scoped commitment hashes, verify the final certified root, obtain local membership paths, build the private witness locally, and prove locally. No private opening, owner, nonce, amount, witness, IPN or private key belongs in a service request. The clients reject private-material field names in public submissions. Default membership lookup is a local tree replay; no per-input commitment query is necessary.

Export produces `{operationIndex, proofBundle}`. The bundle has only `format`, `circuitId`, `manifestSha256`, `target`, `publicInputs`, `proof`, and `rootCertificates`; format is `invisi-provenance-proof-v1`, circuit IDs are `provenance_k<K>`, and target is `evm`. Bundle validation checks scope, generation, configured keys, source ordering, sourcesDigest, capacity, operation digest limb bounds, and binding. A host-supplied prover must also verify its output against the authenticated local VK.

Direct protocol submission and off-chain Provenance submission are two independent SDK steps. Direct preparation, proof generation and calldata export do not require Broadcaster or Source availability. The App chooses whether to call `evaluate_transaction` with a locally generated source sidecar before sending, or `submit_proof` after primary confirmation, then poll the proof job and exact operation recognition. No main transaction is automatically resent. Protocol spendability and off-chain source recognition remain separate.

Explicit preflight can durably admit an opaque tracking task per scope/generation/native operation digest. Retain its ID and use `get_tracking` or its bounded wait. In the explicit `with_broadcaster` path the SDK only builds the source proof locally: Broadcaster performs source evaluation and returns the task in outer quote `provenanceTracking`; the SDK checks its exact operation digest/status and independently reads the same ID from the pinned Source client. It never separately evaluates or resubmits that evidence. The six signed quote fields, policy-bound request hash and v1 format remain unchanged. A generation change requires primary reconciliation and explicit local reproof; it never permits changing already signed calldata. Independent source recovery uses its own encrypted namespace; managed wallet snapshots also retain the public relay/source context needed for their original operation.

Policy-enabled broadcaster quotes bind the original public request hash and required policy with `keccak256(abi.encode("InvisiBroadcasterProvenanceIntentV1", originalRequestHash, policyId))`. The signed Quote's six EIP-712 fields stay unchanged; outer metadata must contain `provenancePolicyId` and `requestHashFormat: "invisi-broadcaster-provenance-intent-v1"`. Missing, unexpected or different policy metadata fails closed. Preliminary fee discovery needs no proof; final quote/submission accepts proof sidecars without changing the signed public intent.

## Rust modules

`invisi_sdk::provenance` (focused crate `invisi-sdk-core`) provides scoped primitives, exact operation digest, strict Ed25519 certificate verification, local recognized tree/path rebuild, `build_witness`, pinned manifest authentication, `validate_proof_bundle`, `export_sidecar`, and an explicit host-injected `OfflineProver` capability. This SDK does not yet ship a native Rust or Rust/WASM provenance proving backend; the trusted host must execute Noir/BB locally and independently verify the returned proof using the authenticated VK. No remote proof endpoint is defined.

`invisi_sdk::provenance_client::ProvenanceClient` supplies scoped machine JSON-RPC methods, `sync_recognized_tree` with an explicit leaf budget, and bounded job waiting. It never changes Note spending state.

`BroadcasterClient::with_provenance_policy(policy)` configures the unified quote/submission client. `verify_quote_for_policy` checks outer metadata and the policy-bound EIP-712 signature; a policy-disabled client rejects unexpected policy metadata. No separate policy quote type is needed.

Golden vector and transport tests: `cargo test -p invisi-sdk-core provenance`, `cargo test -p invisi-sdk-rpc provenance_client`, and `cargo test --test provenance_broadcaster`.

## Signing-key rotation

Pin the provider and genesis signing public key externally. `getPolicy` may return `initialSigningPublicKey` and public `keyRotations`; these fields never establish trust themselves. Verify the complete history (or an explicitly pinned checkpoint including validity intervals) with `verifyRotationChain` / `VerifyRotationChain` / `verify_rotation_chain`. The shared 169-byte rotation payload uses version 1, provider, old/new key IDs, new public key, activation time and previous rotation hash. Verify the old trusted key signature, SHA-256 new key ID, provider, previous hash, strictly increasing activation times and a caller-supplied current time.

Apply the returned keyring explicitly with `withRotationHistory` / `WithRotationHistory` / `TrustContext::with_rotation_history`; the clients do not accept unknown keys automatically. Historical certificates issued before a key's retirement remain valid; that old key cannot issue certificates at or after the successor's activation. `getPolicy` alone permits an unknown reported current key so its history can be fetched for explicit verification; proving, evaluation, submission and job responses still require trusted keys.

Optional service membership lookup requires an explicit interest-disclosure opt-in; returned paths are still checked locally against the trusted certificate. Local paginated replay remains the default.

## Independent recovery coordinator

Recovery is opt-in and separate from Note/Credit inventory, signing, reservations and the App. Construct an encrypted recovery store over caller-owned atomic ciphertext records, then inject the current trusted Provenance client and local host capabilities. There is no default plaintext file store. The AES-256-GCM record purpose/AAD binds `Invisi.Provenance.RecoveryRecord.v1`, the namespaced record key and CAS revision; wrong keys, keys from another record, and stale revisions fail closed. Local revisions are bounded to 2^53−1 in all three languages so JSON/CAS round trips remain exact for TypeScript. The host keeps encryption keys and raw openings separately; recovery records contain only public evidence and frozen public transaction identifiers.

Default `prepare` / `Prepare` first authenticates the frozen statement, calls actual preflight and requires an allowed matching tracking acknowledgement. It persists `deliveryMode: "tracked"`, the tracking ID and the complete sidecar, certificates, scope/policy, manifest, generation, operation digest, ordered input nullifiers, operation index, original calldata/hash, signed request hash and base idempotency key with `broadcast_possible` **before returning permission for external broadcast**. A crash after receiving permission cannot make the record unfrozen. The host continues to own its existing transaction journal and input/nonce reservations. `markBroadcast` records a known transaction hash but is not the safety fence. Local cancellation stops proving/polling and never cancels an external broadcast or releases reservations.

`resume` / `Resume` / `run` first calls the injected host's authenticated reconciliation of the original frozen transaction. In tracked mode it polls the persisted tracking capability, checks any matched locator against primary reconciliation and confirms the exact operation through `getOperationRecognition`; it never automatically submits another copy of the source proof. Missing tracking does not silently downgrade. In explicit `prepareDirect` / `PrepareDirect` / `prepare_direct` mode, confirmed locators are persisted before source submission. An uncertain direct-mode network response is retried with the same key, derived as `base:SHA256(canonical JSON proofBundle)` (base: 1–63 printable ASCII bytes, must not start with reserved `internal/`, derived key: at most 128 bytes; checked before permission); a replacement bundle gets a different submission key. The original calldata, callee/scope, token, ordered nullifiers and operation digest remain frozen. The signed request hash also remains fixed, so the coordinator never silently changes nonce, fee or quote. The host must decode/authenticate this frozen transaction and independently verify local proofs; these are required capabilities, not trust inferred from a service response.

In explicit direct mode, after proof submission the coordinator stores the job ID and polls it. **A `valid` job only sets `proofValid`; completion requires `getOperationRecognition` for the exact canonical locator and matching operation digest/nullifiers to return `recognized` with its operation checkpoint.** Mixed funding or dependencies can remain `pending_source` or `source_rejected`; provider outages leave resumable state, and resuming a rejected source operation can observe a later decision without changing any old Note's status. No output Note is required, so a zero-output withdrawal still completes through operation recognition.

Tracking responses are scoped trusted envelopes containing `tracking: {id, status, expiresAt, operationDigest, matched?, reasonCode?, checkpointSequence?}`. IDs are 48 lowercase hex characters; queries send the locally pinned policy. Single-operation evaluation has `tracking` on its flat decision; aggregate decisions each carry their own tracking, selected by operation index. States are `pending_confirmation`, `pending_source`, `recognized`, `expired`, `superseded`, and `stale_generation`. Matched/published states require a concrete transaction/block/member locator; SDKs reject unknown states, untrusted identities, mismatched digests/locators and stale-generation capabilities. `expired`/`superseded` are terminal and never trigger another transaction. `expiresAt` is canonical decimal seconds; only the service's authenticated mature chain prefix can establish expiry, so local clock/index lag does not itself expire a task. Bounded waits can time out and be resumed. No-proof public funding/Credit lifecycle operations are already indexed and do not need tracking.

Tracked reproof re-evaluates the unchanged candidate and persists a fresh/coalesced tracking ID before continuing. If the already-mined candidate's original deadline prevents a new preflight, the host must explicitly choose `prepareDirect` with a locally regenerated sidecar and authenticated mined locator; the SDK never changes its deadline/nonce/fee/quote or silently bypasses tracking. Raw openings remain exclusively in host-encrypted storage/local proving capabilities.

Current job wire states are `queued`, `verifying`, `retryable_error`, `valid`, `invalid` and `stale_generation`. `retryable_error` keeps the same job pending for the worker to retry; `invalid` becomes local `proof_rejected` and allows explicit local reproof with a different bundle-derived key. `stale_generation` requires fresh host reconciliation and reproof. Unknown spellings fail closed; none of these cryptographic-job states is a funding/source risk rejection. Public `waitProofJob` returns terminal `stale_generation` immediately and rejects unknown states.

Recovery completion is confirmed by the pinned source service's operation-recognition response under the configured trust model. It is not independent authentication of output Note membership. Receivers still separately authenticate root certificates, canonical anchors and membership when accepting a Note.

A generation change or reorg returns `needs_reproof` after host reconciliation. With explicit local reproof enabled, the host may supply a new sidecar only after the service trust context is explicitly updated to that generation; the coordinator rechecks certificates, binding, ordered input digest and the entire frozen statement. No remote proving URL or raw opening argument exists. On interruption/restart, instantiate another coordinator over the same encrypted records and call resume/run with the same ID. Local `filterRecognizedCommitments` / `FilterRecognizedCommitments` / `filter_recognized_commitments` helpers filter through a rebuilt `RecognizedTree`; protocol spendability and source recognition remain separate, with no per-note network interest query.

Recovery state-machine tests use explicitly marked synthetic proof bytes and real signed root certificates; they validate recovery/encryption behavior and do not claim another native-prover or App integration test.

Rust: `provenance_store::SessionRecoveryRecords::new(existingAtomicRecords)` adapts existing session `AtomicRecords` (including optional `SQLiteRecords`) to `provenance_recovery::EncryptedRecoveryStore::new(Arc::new(adapter), key32)`. Construct `RecoveryCoordinator` with explicit store/trust/service/host references; a successful `prepare` is the broadcast permit. `AtomicBool` cancellation and optional local reproof remain host-controlled; the coordinator delegates proving to its explicit local capability. `prover::NativeSourceProver` is an available local Noir/BB adapter with separate source manifest/VK authentication and independent verification.

## Normal prepared transactions

Configure `Invisi::with_provenance(Arc<PreparedProvenance>)` with a pinned client, authenticated local manifest, local `OfflineProver` and explicit `SourceReplayBudgets`. After normal Note discovery and `prepare_transfer`, call `prepared.with_broadcaster(chain, relay, &BroadcasterOptions::default())` **before** wallet approval or main proving. The method borrows the original and returns a detached prepared transaction; fee convergence, source denial, local cancellation or quote failure leaves the original usable.

Fee convergence rebuilds candidates from the original business preparation. Only the final fee-bearing plan obtains a local source proof and the Broadcaster-provided tracking acknowledgement. The SDK first reads the current checkpoint, authenticates its certificate and primary-chain anchor and rebuilds its public recognized tree. If required, bounded root-history pages select the latest certified prefix per physical tree. Certificate/page/total-leaf budgets fail explicitly; no per-Note recognition request is made. Input nullifier order remains the native statement order, with independent source capacity selected from all 28 tiers.

The final prepared transaction retains its verified quote, deployment/relay/policy identity, original intent hash, public sidecars and automatic tracking. Broadcaster performs the policy preflight; the SDK does not call source evaluation in this path. Run the existing wallet authorization and main proving methods, then `submit_broadcaster(chain, relay, id)`; submission validates the saved context and attaches its saved sidecars internally. Funding nonce/deadline freeze before the quote; `with_funding_terms` cannot change them afterwards. The existing funding-signature attachment remains allowed and cannot change the unsigned intent. A changed business plan requires explicit preparation/repricing and new source evidence. There is no automatic resend.

`Operation::with_broadcaster(&mut self, relay, options)` atomically stores the final public context in the existing encrypted wallet journal before consent, for both funds and all four Credit operations. `Operation::submit_broadcaster` stores the original broadcaster ID, exact calldata and externalization fence together before the first network send. After restart the same ID first queries the authenticated relay journal: a known result returns without new proof, preflight, Source capability or primary freshness reads. A changed ID/configuration is rejected; a lookup outage never triggers another send. Only the current wire's explicit unknown-request response permits fresh validation and another attempt with the same frozen ID/body. Primary reconciliation remains necessary to finalize wallet state; a relay status alone never authenticates source recognition.

Runtime client/prover capabilities are never serialized. Restored operations reattach configured capabilities when present; known relay-journal retries work with the Source capability absent. A pre-quote Credit snapshot reconstructs its business plan from its validated financial state and optional public draw-recipient address. Quoted snapshots retain their frozen context and do not silently reprice or replace a transaction.

Shield/zero-input and Credit lifecycle calls skip Note source proving. Only Broadcaster performs the configured policy evaluation in the explicit relay path. `PreparedCredit::with_broadcaster` supports create, update, draw and revoke before consent; it rebuilds the final fee-bearing native statement and invalidates earlier consent/proofs. Create/update/revoke fees remain owner-paid. Draw payer debits and successor grant accounting stay gross; the recipient Note is rebuilt and encrypted for `totalDebit - fee`, which must remain positive. Revocation obtains EVM consent after the fee/quote is frozen. Unsupported-token `getFee` errors stop before consent, proving or source submission and never silently select the direct path. Aggregated relay broadcast remains unsupported.

## Normal examples

The existing [`03-note/transfer.rs`](examples/03-note/transfer.rs) and [`withdraw.rs`](examples/03-note/withdraw.rs) show discovery → preparation → automatic source/quote attachment → host approval → main proof → optional relay submission. Set `SOURCE_CONFIG` to trusted public `LocalProvenanceConfiguration` and `BROADCASTER_CONFIG` to the registered relay configuration. `PreparedProvenance::from_local_configuration` authenticates the local source manifest and signing-key ID and installs a `NativeSourceProver`; no example assembles private source witnesses or public sidecars. The configured pin/key must come from the operator, never a service response. This simple file configuration pins one active signing key; applications that need verified rotation intervals can still construct the explicit `PreparedProvenance` capability with their validated trust history.

These same Note files offer `--confirm` using `BROADCAST_RECORD` plus `TRANSACTION_HASH`. This authenticates the retained relay configuration and actual primary transaction/receipt/block, waits for automatic source tracking and confirms the exact operation recognition. It does not resubmit the source proof or main transaction. See [`examples/README.md`](examples/README.md) and the public `source.example.json`/`broadcaster.example.json` templates.

The existing [`04-credit/create.rs`](examples/04-credit/create.rs), [`update.rs`](examples/04-credit/update.rs), [`draw.rs`](examples/04-credit/draw.rs) and [`revoke.rs`](examples/04-credit/revoke.rs) all use the same highlevel `with_broadcaster` and `submit_broadcaster` pattern. Without `BROADCASTER_CONFIG`, their independent direct host flow remains available. The SDK does not automatically contact Source or enforce a Source completion gate on direct protocol submission.
